# Changelog

Changes to the GASP Standard and to the `gasp-standard-mcp` package, newest first. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the package follows [semver](https://semver.org/). Changes to the standard's content are listed under the package version that first shipped them, since the package bundles the standard. `DECISIONS.md` has the reasoning behind each rule.

## [Unreleased]

### Added
- A sixth CEL event class, `Credit_Event`, on the `credit_event` dataset: the prepaid balance ledger as billing systems keep it (purchase, consumption, expiry, adjustment; signed `credit_amount`; `consumption_basis` committed, overage or on demand; optional balances before and after; `expires_on` on purchases). Seven Finance metrics read it: Consumption Revenue, Usage Run-Rate (the trailing three months of on-demand consumption, annualised), Prepaid Credit Balance, ARR Including Usage Run-Rate, Credit Breakage, Consumption Revenue Growth Rate and Consumption Net Revenue Retention. MRR, ARR, NRR and GRR are unchanged; consumption pricing with or without a commitment is in scope. 313 metrics, 280 fields, 54 datasets, 301 formula entries. The decision and the sources: `DECISIONS.md` 2026-11-08 and `docs/usage-based-proposal.md`.
- `cel.md` "Deriving Credit Events": the usage realisation pair derived from the credit ledger's overage consumption by calendar month, and consumption events with basis overage derived from `usage_record`. `derive_cel` gains `usage_source` (`usage_record`, the default when the mapping covers it, or `credit_event`) and `target` (`revenue_event`, the default, or `credit_event`).
- `generate_checks` gains `credit_balance_identity`: where both balances are mapped, before plus amount equals after on every purchase, expiry, adjustment and committed consumption row, and the two are equal on an overage or on-demand row.
- The Stripe worked example maps Stripe's billing credits (credit grants and credit balance transactions, copied from the API by the company's nightly job) to `credit_event`: a paid grant is a purchase, an application committed consumption, an expiry an expiry and the rest adjustments; with no running balance on Stripe's ledger the balance identity check names what it lacks. The test computes Consumption Revenue, Prepaid Credit Balance and Credit Breakage over the sample.
- GASP Workspace, step 1: identity and storage on the hosted server, off unless `WORKSPACE_DATABASE_URL` and `WORKSPACE_ISSUER` are both set (`src/workspace/`). The HTTP entry point becomes an OAuth resource server in the MCP authorization flow with WorkOS AuthKit as the authorization server: it serves the protected-resource metadata at `/.well-known/oauth-protected-resource` (and with the MCP path appended), reads each POST body before the transport, and answers a `tools/call` for a protected tool without a valid token with a 401 whose `WWW-Authenticate` header names the metadata (`error="invalid_token"` and the reason when a token was refused), so the client sends the user through sign-in. The protected tools default to the ten implementation tools and the two new ones (`WORKSPACE_TOOLS` replaces the list); every other request is untouched, so the twelve tools that read the standard stay anonymous. A token is verified against the issuer's keys (`jose`; signature, issuer, expiry and `aud` when `WORKSPACE_AUDIENCE` is set) and must name an organisation (`org_id`), which is the company. Two tools, served only with the Workspace on: `save_workspace` writes the mapping, the semantic model, the decisions and the check results, each checked the way the pipeline tools read it, as the next version of its kind, and `load_workspace` reads the latest of each back or lists the versions. Storage is Postgres (`companies`, `members`, `documents`; the first member of a company is its admin, a new company gets a thirty-day trial), through `pg` loaded on first use, with every statement scoped to one company. Tool call records gain `company`, the organisation id, never the user. The stdio binary and a hosted server without the Workspace behave as before. `test/workspace.test.ts` runs the store on PGlite and the server against a local key set: the metadata, anonymous free calls, the challenge with and without a token, a save read back by its company and by no other, and the record carrying the company and no user.
- A `compile_target` tool that writes the metrics your mapping covers as the files of a semantic-layer engine, the step after `compile_model` for a team whose agents read Snowflake or Cube rather than an Ossie model. It takes the same input, compiles the metrics the same way and writes them in the warehouse's SQL: `target: snowflake` gives a Cortex Analyst semantic model YAML (every table with a `database.schema.table` base table, its key, time dimensions, dimensions with sample values from the enum fields, facts, the joins GASP declares and the `gasp_` metrics) and `staged_views.sql` (the period spine table and one view per staged metric, its body the compiled Snowflake source), and `target: cube` gives a Cube data model (a cube per table with its joins, dimensions and measures, and one view joining the cubes from `revenue_event`). The Apache Ossie converters it replaces pass `SUM(x) FILTER (WHERE w)` through, which Snowflake does not run, and read the Postgres staged source whatever the warehouse; here the emitter writes each direct metric in the target dialect (`dialect` on `EmitContext` in `ossie/metrics.ts`: the filter as a `CASE` inside the aggregate, the date differences, numerator cast and percentiles from `dialect.ts`) and the staged queries are compiled in it. The Ossie export is unchanged. `src/targets/` holds the neutral target model and the two writers. `test/targets.test.ts` checks every direct metric's Postgres expression against its `OSSIE_SQL_2026` value on the fixture and the other dialects for forbidden tokens, the Acme adapter's Snowflake files (MRR as `COALESCE(SUM(CASE WHEN subscription.subscription_status = 'active' THEN subscription.mrr END), 0)`, each view the compiled source) and the fixture's cubes, whose measures and staged queries give the canonical values on PGlite. Findings behind it: `docs/compile-targets-spike.md`.

### Changed
- `derive_cel` is titled "Derive revenue and credit events" (was "Derive CEL revenue events"), since it also writes `Credit_Event` rows. The tool name is unchanged, so no client or prompt is affected.

### Fixed
- A period shift or trailing window taken from a month's last day no longer lands short. `lag(x, 1 month)` over February ended on 28 January and `window(x, 3 month)` ending 30 June started on 31 March, so events dated on a month end (invoices, consumption, month-end postings) fell out of the lagged period or into the window one month too many. An end bound now shifts as the day after it, stepped back a day, and a window starts the day after `end - n` (`compile.ts`). Metrics over the synthetic dataset are unchanged except where a row sits on a month end; the Ossie staged sources and the conformance set are regenerated.

## [1.19.1] - 2026-11-07

### Added
- Three guards on the HTTP entry point for a public endpoint, each configurable and off at 0: a per-client rate limit on the MCP path (`MCP_RATE_LIMIT`, default 60 requests a minute; the client is the first `X-Forwarded-For` entry behind a proxy, else the socket; beyond it a 429 with `Retry-After`), a request body cap (`MCP_MAX_BODY_BYTES`, default 1 MB; over it a 413, a body without `Content-Length` a 411) and a cap on how many `score_drift` and `readiness_report` calls, the two that load PGlite, run at once across the process (`MCP_HEAVY_CONCURRENCY`, default 2; beyond it the tool returns a busy error the client can retry, `HEAVY_TOOLS` and `BUSY_TEXT` in `server.ts`). The stdio binary has none of them. Four tests in `test/server.test.ts`.

### Fixed
- Every tool's `title` is now the top-level field of the tool as well as `annotations.title`: the tools are registered through `registerTool`, so a client that reads only the top-level title, such as the Claude connectors directory portal, sees it. `test/server.test.ts` checks both.

## [1.19.0] - 2026-11-07

### Added
- A Streamable HTTP entry point, `gasp-standard-mcp-http` (`build/http.js`, `npm run serve`), for a hosted endpoint Claude connects to as a remote server: stateless, one server per request over the data loaded once, `PORT`, `HOST`, `MCP_PATH`, `MCP_ALLOWED_HOSTS` and `MCP_ALLOWED_ORIGINS` from the environment, `/` and `/health` answering with the version and tool count, and one JSON line on stderr per tool call (`event`, `tool`, `ms`, `ok`, `client`; never the arguments or the result) so the host's log stream counts calls per tool (`createServer({ onToolCall })` in `server.ts`; the stdio binary records nothing). The tools moved from `index.ts` into `server.ts` (`createServer()`), which both entry points share; `index.ts` is the stdio binary as before. Every tool now carries a `title` and the annotations `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true` and `openWorldHint: false`, which the Claude connectors directory requires and which let a client run them without a per-call prompt. A `Dockerfile` serves the published package. `test/server.test.ts` lists the tools over an in-memory transport and over HTTP, checks every title and annotation, and checks that an origin the server was not told to allow is refused.
- The Ossie readers accept `custom_extensions[].data` as a JSON string (the form the pinned `OSSIE_VERSION` defines) or as an object (the form apache/ossie #522 proposes, which GASP backed on dev@ on 2026-11-04). `parseDocument` rewrites an object payload to the pinned string on the way in, so `validate_mapping`, `compile_model`, `score_drift`, `record_decision` and `readiness_report` give the same report for either form; `checkExport` and the demo and compiler readers decode either in memory (`extensionData` in `ossie/types.ts`). The same readers accept the key `nonportable_extensions`, which the proposal renames `custom_extensions` to with the guardrails agreed on dev@ on 2026-11-05: `parseDocument` folds it back to the pinned key (after any entries already under it) so every tool reads either key. The writers keep emitting the pinned form under the pinned key. A document with object payloads, the renamed key or both round-trips through `validate_mapping`, `compile_model` and the checks with the same report as the pinned form, and a bad object payload is named by its placement.

## [1.18.0] - 2026-11-04

### Added
- The CEL derivation rules, two more sources. `standard/cel.md` gains "Deriving Revenue Events from an Invoice Ledger" (an invoice is one service period whose MRR is its `recurring_amount` over the months the period covers, whole months for monthly, quarterly and annual billing; a subscription's MRR on a date is the sum over the invoices covering it, its ledger dates are the starts of its service periods and the day after each end, no date after the ledger's horizon, the latest service period start, is read, and the subscription rules then apply) and "Deriving Usage Realisation" (a period whose `usage_amount` exceeds its `committed_amount` adds an `expansion` dated the period's end for the overage as MRR, tagged `usage_realisation` with `change_nature` `temporary`, and a `contraction` the next day with `change_nature` `scheduled_reversal`; usage within the commitment is no event, since the commitment is already in MRR, and the pairs chain with the ledger's steps). The ontology gains `subscription_id`, `service_period_start`, `service_period_end` and `recurring_amount` on the `invoice` dataset and the `usage_record` fact dataset (`subscription_id`, `customer_id`, `period_start`, `period_end`, `committed_amount`, `usage_amount`, `currency`): 274 fields across 53 datasets. The reference SQL of both is printed in `cel.md` and equals the module's.
- `derive_cel`: `source: invoice` reads the invoice dataset in place of the subscription dataset, and the usage records are read whenever the mapping covers `usage_record` (`usage: false` leaves them out, `usage: true` asks for them). The report names the source's limits (an invoice ledger shows a mid-period change on the next period's start, never sees a change an annual invoice does not bill and carries no segment) and the usage pairs. The synthetic dataset gains service periods on its monthly invoices and usage records for three committed customers; the tests derive seven month-start movements from the invoices (a corrected invoice read at its latest snapshot, a fortnight's invoice stated as MRR, overlapping invoices summed, a one-off skipped) and six usage pairs (a quarter's overage stated as MRR, a period met exactly or under a cent over giving nothing).
- The Stripe worked example gains a metered API item (no MRR of its own) with three usage records built by the nightly job from the metered invoice lines, so `derive_cel` over it yields sixteen events: the twelve ledger movements and two usage pairs; its invoices carry the service period and amount of their licensed lines, and the invoice source derives nine events from them, showing what an invoice ledger cannot say (a seat add folded into the next month's invoice, a churn dated the end of the last paid period, an annual plan's seat reduction unseen). `classify.sql` leaves the tagged usage events alone.
- `profile_schema`: a table with `period_start` beside `period_end` is a per-period row dated its start, no question asked; a start date beside its end date elsewhere is still a span the business settles.

## [1.17.0] - 2026-11-04

### Added
- Two vendor worked examples beside Acme in `gasp-wiki-mcp/test/fixture/`, written from public API documentation and never standard content (`DECISIONS.md` 2026-11-03): Stripe on Redshift (`stripe/`: the Data Pipeline tables, the nightly snapshot job that gives Stripe's current state a history, a GASP mapping at subscription item grain with MRR normalised from the price's interval and the statuses recoded, a sample ledger, the twelve revenue events `derive_cel` derives from it, a step that fills the ATL expansion tag from the item history and the company's own metrics) and Salesforce on BigQuery (`salesforce/`: the landed objects in a connector's spelling, mapped to the opportunity, lead, customer and campaign datasets with every picklist recoded). `test/vendor-fixtures.test.ts` takes the Stripe example from a validated mapping to readiness level 4 on PGlite and its drift report names the planted difference (Net New MRR without reactivation), the interop spec's phase 3 exit criterion; the Salesforce example validates, compiles Win Rate and Pipeline Value and the checks in BigQuery, profiles, and stops at level 2 because a CRM maps no revenue event.
- `readiness_report`: the readiness report (`src/readiness.ts`), closing the pipeline's Publish step. It reads which of the interop plan's four levels a company has reached from the documents the other tools wrote: L1 Profiled (a semantic model exists), L2 Mapped (a metric fully covered and no profiler question or proposer candidate open), L3 Clean core (the CEL revenue events mapped, the checks run and every covered Core metric passing every check that protects it) and L4 LLM-ready (the canonical metrics compiled into the model and none of the company's own metrics differing from its canonical counterpart, scored as `score_drift` does). Levels are cumulative; each blocker names the tool that clears it and the Next line is the one action to take. The test suite takes the synthetic dataset to L4 with the fixture adapter, the pasted check rows and the compiled model, the interop spec's phase 3 exit criterion.
- Readiness checks, second round. `generate_checks` adds a range check per fully mapped metric with a hard min or max in the ontology (`range:<formulaId>`: NRR at least 0, GRR at most 100%, Gross Margin, Logo Churn, Revenue Churn, NPS, LTV:CAC, CAC Payback, DAU/MAU, ARR), evaluating the compiled template once per row of the period spine (`period_spine`, the table `compile_model` reads) and counting the periods out of range; a percent rule on a percent formula is divided by 100 since GASP ratios are unscaled (`src/ranges.ts`). `score_drift` flags the company's own values outside the same ranges per period, matches a metric name or synonym ending in -O or -M to that declared form (NRR-O, cac_m) and scores the O/M bridges (metrics/core.md): where both forms of a dual-lens metric are matched, the gap between them on the company's numbers beside the canonical gap per period, named by its diagnostic (the Durability Gap for ARR, the Expansion Integrity Gap for NRR, the Activation Delta for CAC, the Contribution Leakage for LTV, the Services Drag for Gross Margin). A planted Durability Gap (operating ARR equal to reported ARR) and a value below NRR's minimum are named in the tests.
- GASP Ossie extension schema (`standard/gasp-ossie-extension-v1.json`, served at https://gaspwiki.com/schemas/gasp-ossie-extension-v1.json, bundled as `extensionSchema`). It describes the GASP `custom_extensions` payload on the model, a dataset, a metric and the mapping, strict so every key GASP adds outside Ossie is listed, and the cross-document checks behind the export, `validate_mapping`, `compile_model`, `propose_mapping` and `record_decision` now reject any GASP payload that does not match it.
- `generate_checks` and `plan_fixes`: the Check and Plan steps of readiness level 3 (`src/checks.ts`). The checks are the rules the standard already states, compiled over the datasets a mapping covers in its dialect: CEL row identity (`prior_mrr + mrr_change = new_mrr`), MRR continuity (`mrr_start` equals the previous snapshot's `mrr`), unique `event_id` per event dataset, the three ATL tags (a lifecycle tag on every event, an expansion classification on every expansion, contraction and reactivation revenue event and every amendment, a cost function on every cost event), customer identity both ways and freshness per dataset within a window. One statement, one row per check; GASP has no warehouse access, so the company runs it and pastes the rows back as `results` for pass or fail per check and per metric, each check naming the metrics whose formulas, or O and M forms, read what it covers. `plan_fixes` ranks every unmapped field and every failing check by the Core metrics it unlocks, then all metrics, then the metrics it helps, with an effort class shown and used only as a tiebreak; a fix unlocks a metric when it is the last thing between that metric and covered-and-passing. Left out on purpose: the O/M bridges and the ontology's value-range rules (`DECISIONS.md`). The synthetic dataset passes every check; a table of planted violations fails the right ones by the right counts; the events `derive_cel` writes fail only the expansion tag. The server has 21 tools.
- `derive_cel`: the Build CEL step of readiness level 3 (`src/cel.ts`). It takes the same mapping as `generate_query` (a GASP adapter or an Ossie mapping with its semantic model) and the ledger's currency, and returns the SQL that derives CEL `Revenue_Event` rows from the subscription dataset the mapping covers, by the rules below, in the dialect asked for or the one the warehouse names, with the fields the mapping lacks listed and a note on what the ledger can and cannot say. On the fixture adapter the SQL runs and yields every synthetic movement; on the Acme adapter it compiles in Snowflake and names the unmapped `segment`. `first_snapshot: steps` is for a ledger that starts with the business. The server has 19 tools.
- The CEL derivation rules: `standard/cel.md` gains "Deriving Revenue Events from a Subscription Ledger", the vendor-neutral rules that turn the GASP `subscription` dataset (snapshots or a version history, at any cadence) into `Revenue_Event` rows: a step is a change in a subscription's active MRR, the ledger's first date is the opening balance, one event per step dated the snapshot that first shows it, `prior_mrr` and `new_mrr` are the customer's MRR chained through the customer's steps so the row identity holds, the event type from the customer's MRR around the step, ATL lifecycle tags and defaults, an empty `expansion_classification` because the ledger cannot say what kind of expansion it was and the netting a coarse cadence causes. `src/cel.ts` writes the SQL with the compiler's placeholders in all four dialects (`revenueEventDerivation`, which `fillTemplate` compiles over any mapping that covers the six fields), and `test/cel.test.ts` runs it over the synthetic dataset: every generated movement comes back row for row, the monthly sums agree with the compiled MRR movement metrics, month-end snapshots give the same net change dated the month end and the SQL printed in `cel.md` is the one the module writes. Several subscriptions of one customer changing on one date are typed from the customer's MRR at the start and end of that date. The ATL gains assignment rule 8: `contraction` and `churn` carry the `retention` tag. The dialect table gains a text cast for the event id.
- `record_decision`: the Decide step (`src/ossie/decide.ts`), closing readiness level 2. It records the decisions people make on a profiled and proposed warehouse. Each decision names what it is about, its subject by content and its owner: a profiler question answered (the key, the time field, the kind or a datatype, written into the model), a candidate accepted or rejected (a table as a GASP dataset, with its columns matched as the proposer would; a column as a GASP field, with an optional transform that becomes a calculated field), a metric owner (the slot `validate_mapping` reads) or a judgement call GASP cannot apply (which system owns customer identity, the reporting currency, what date marks churn), recorded with its answer. Every decision lands in the mapping's GASP extension; a later decision on the same subject replaces the earlier one. With no decisions it lists what is open: the questions no decision or model state has settled, the candidates no decision has settled and the covered metrics without an owner. Level 2 is reached when no question and no candidate is open. The profiler now writes its questions in full into each dataset's GASP extension and the proposer its candidates and unmatched tables into the mapping's, so the step reads the documents alone. On the Acme proposal the two planted questions, the two candidates, two rejected pairs, two owners and two judgement calls reach level 2 and the result passes the upstream validator; on the synthetic dataset's own schema the five questions and the one candidate decided give every field pair of the fixture adapter. The server has 18 tools
- `propose_mapping`: the mapping proposer (`src/ossie/propose.ts`), readiness level 2. It takes the semantic model `profile_schema` returned (or a company's own, or a schema profiled on the way in) and proposes a GASP mapping: every table is scored against every GASP dataset on how many of its columns find a field there, its profiled kind, key and time field against the dataset's declared ones and its name; every column of a proposed table against the dataset's fields by the same name, the structural role (the table's time field is the dataset's date, its key the dataset's key), a short synonym and abbreviation list, the same words in another order or a near name, each checked against the warehouse type and, for an enum field, the listed values. A column in cents gets a `{{value}} / 100` transform and enum values the standard does not use a `CASE` recode when the recode table knows them (upgrade to expansion). Only high-confidence pairs enter the mapping, an Ossie mapping over the model with a calculated field per transform; medium ones are listed as candidates with their evidence and what would settle them; the rest are unmatched. On the synthetic dataset's own schema it proposes all 52 tables and every field pair but one near name, a candidate; on the Acme DDL it reproduces the Acme adapter with both transforms. The Acme DDL fixture now places each column on the table of the dataset the adapter resolves it to
- `profile_schema`: the schema profiler (`src/ossie/profile.ts`), readiness level 1. It takes a warehouse schema as the rows of `information_schema.columns` (JSON or CSV), a tables list or `CREATE TABLE` statements, with optional per-column statistics (`output: statistics` returns the standard SQL that gathers them), and returns a minimal Ossie semantic model: one dataset per table with its fields and datatypes, the key, the time field and the kind (snapshot, event, fact or reference) inferred from declared constraints, names and statistics, each with its evidence and confidence in the GASP extension, and the relationships the columns imply. What the names cannot settle (a span table's date, two foreign keys and no own id, a per-period table with no id, an opaque type) is listed as a question for the Decide step and left out of the model. On the synthetic dataset's own schema the names alone give every table the ontology's time field and kind but one and the key of all but five; statistics settle three more and leave one honest tie. Fixture: `test/fixture/acme-schema.sql`.
- `score_drift`: drift scoring by result (`src/ossie/drift.ts`). It takes the mapping in either format and the company's semantic model, matches each of their metrics to a GASP metric by exact name, `ai_context.synonyms` or an explicit `matches` pair (near names are listed for review, never scored), compiles the canonical metric into their dataset and field names and runs both on the GASP synthetic SaaS dataset for six monthly periods in PGlite. Each difference carries both values per period, the largest difference and the likely cause read from the canonical formula: a null on one side (a sum over no rows that is NULL in the company's SQL and 0 in GASP's, or a canonical average or ratio with nothing to read), a staged construct the expression cannot state (a cohort, an opening value, a period bound to a business date), an enum filter one side applies, a dataset one side reads, an aggregate whose value has no equal on the other side. Metrics reading unmapped fields are reported as not runnable with the field named. `output: json` returns the data.
- The synthetic SaaS dataset moved into the package as `src/synthetic.ts` (the test fixture re-exports it), so the published server can build it; `loadSynthetic` loads it into any SQL runner. `@electric-sql/pglite` is an optional dependency, imported on first use.
- `compile_model`: the metric compiler into a company's Apache Ossie model (`src/ossie/company.ts`). It takes the same input as `validate_mapping` and returns the company's semantic model with a `gasp_` metric for every formula entry the mapping covers: a direct `OSSIE_SQL_2026` expression over their datasets and fields, or a `gasp_staged_` per-period dataset whose `source` is the compiled SQL over their tables in their warehouse dialect, reading a period spine table they name (declared as `gasp_period_spine`). Entries reading unmapped pairs are listed with the pairs they need; `metrics`, `department`, `dialect`, `period_spine` and `output` narrow or shape the result; recompiling replaces the earlier additions. The compiled metrics are checked against the bundled Ossie model schema and GASP's reference checks. The exporter now builds metrics over a `ModelTarget`, with the reference model as one target.
- `validate_mapping`: one mapping format. The tool takes a GASP adapter (JSON) or an Apache Ossie mapping document (YAML or JSON) with an optional `semantic_model`, converts an adapter on load into an Ossie mapping over a model synthesised from its tables and columns, and reports in layers: the bundled Ossie schemas, GASP's cross-document checks against the GASP ontology, then the coverage, transform and ownership checks. `validate_adapter` stays as the same tool under its original name; `generate_query` accepts either format. The upstream Ossie schemas travel in the bundled data as `ossieSchemas`.
- A runnable demo for the Ossie example at `standard/exports/ossie/example/demo/`: data, one query per Core metric and the expected values, for DuckDB or Postgres; written by `npm run conformance` and checked on DuckDB in the test suite.
- Ossie portability profile: `coverage.json` tags each direct metric with the upstream `compliance/portability` rung (M0 to M3) its construct needs and lists the constructs the held rungs will measure, with a summary under `portability`.
- A compact example for Apache Ossie at `standard/exports/ossie/example/`, written by `npm run derive`: the Core department (39 metrics over 6 datasets) as an ontology, a semantic model and a mapping in the layout of the upstream flights example, cut from the full export so every statement matches it.
- A conformance set for Apache Ossie at `standard/exports/ossie/conformance/`, written by `npm run conformance`: one case per construct the portable language cannot state (the eleven staged reasons), each a complete Ossie model, a Postgres reference query, the expected result as standard SQL and the fixture rows it reads. `manifest.json` and `README.md` describe the cases.

### Fixed
- Test fixture: contraction and reactivation revenue events and downgrade amendments now carry an `expansion_classification` (`same_product`), as ATL rule 2 requires; the new readiness check found them missing. NRR-M on the fixture now counts the June reactivation, as its formula intends; the conformance set and the example demo carry the rows.
- The site workflow failed after the drift scorer landed: `npm test` regenerates `src/data/acme-drift.json` after `npm run build`, and the dist-staleness guard did not list it among the generated files. The build itself was fine
- `propose_mapping` mapped a bare `status`, `type`, `kind` or `stage` column to the first field with that suffix in the ontology; where a dataset has several (partner has `certification_status` and `partner_status`) it now takes the one named for the dataset, and the rule outranks a near-name guess
- `profile_schema` named a question's dataset by the bare table name while the model qualified it by schema when two tables shared a name, so a decision could land on the wrong table. The statistics query no longer double-quotes identifiers (Snowflake folds unquoted names to upper case, so a quoted lower-case name did not match) and takes a `dialect` for the string cast (BigQuery and Databricks have no VARCHAR)
- `score_drift`: a `matches` pair naming a metric with a colon in its name (`LTV:CAC Ratio`) was read as a form suffix; the `semantic_model` description claimed any document with a metrics list would do, which is true only with a GASP adapter
- `record_decision`: an owner decision rebuilt the mapping's concept mappings when only the extension changes; `propose_mapping` reported coverage over all 306 metrics where `validate_mapping` counts the 294 with a formula
- `expressionText` prefers the portable `sql` form, then the OSSIE_SQL_2026 dialect, so a company model written in upstream's canonical form is read right
- An ordered-set aggregate's `WITHIN GROUP` clause now belongs to its aggregate span, so a percentile metric in the example demo and the compiler's direct queries is evaluated as one call rather than cut at `PERCENTILE_CONT(p)`.

### Changed
- `generate_checks` and `plan_fixes` take `period_spine` (default `gasp.period_spine`) for the range checks; `readiness_report` takes the same options as both plus `matches`.
- Every expression GASP writes is the portable `sql` form alone (`expression: { sql: ... }`), the field the pinned Ossie schema calls authoritative and upstream's canonical examples use since apache/ossie#640 (2026-11-03), instead of a one-entry `dialects` list. The exporter, the adapter converter, the company compiler, the drift scorer's views, the profiler and the proposer all write it through one `portable()` helper; every reader (`expressionText`, `portableEntries`, the cross-document checks, the example cutter, the demo) accepts either form, so a company model written with `dialects` still works everywhere. The 13 committed export files, the conformance set and the example change shape only; no expression text or expected value changes.
- A `sum()` over no matching rows is 0. The compiled SQL templates emit `COALESCE(SUM(...), 0)` and the direct Ossie expressions `COALESCE(SUM(x) FILTER (WHERE w), 0)`, so a metric that adds movement types (Net New MRR, NRR, GRR) has a value in a period where one type had no event; before, it was NULL in such a period (monthly NRR on the fixture was NULL in five of six months). `count` was already 0; `avg`, `min`, `max`, `median` and `percentile` over no rows stay NULL, as does a ratio over a zero denominator. The staged sources, the conformance set and the example demo carry the new SQL; every expected value in them is unchanged because their period holds every movement. The portability profile counts the wrapper as the `null guard` construct (85 direct entries) and no entry is a bare M0 sum. `score_drift` names a null on either side as a cause.
- Test fixture: two expansion events now carry the `pricing_adjustment` and `recontracting` classifications, so the Operating forms of ARR and NRR compute on it (the conformance data and the example demo carry the rows).
- Every filtered direct metric in the Ossie export uses the aggregate filter clause, `SUM(x) FILTER (WHERE w)`, which `OSSIE_SQL_2026` requires since apache/ossie#382, in place of `SUM(CASE WHEN w THEN x ELSE 0 END)`. `checkExport` accepts the clause and rejects `CASE WHEN` filtering.
- The Ossie export labels every staged dataset's `source` with the registered Ossie dialect name `POSTGRES` (`source_dialect` in the GASP extension), which `apache/ossie#598` added to `extensions/dialects.md` on 2026-11-01. `OSSIE_DIALECT_OF` in `src/dialect.ts` now covers all four compiler dialects. The Snowflake, BigQuery and Databricks sources still travel under `sources` because a dataset `source` is one string.
- The vendored upstream validator is pinned at `apache/ossie@99c21c2` (2026-11-02), up from `2b1f9bf`. It now cross-checks the mapping against the ontology and model its `iri`s name and checks relationship columns against the model's fields; the three GASP exports pass unchanged. The vendored copy gains `python/src/ossie/_loading.py`, which the script imports.
